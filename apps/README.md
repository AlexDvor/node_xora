# NodeXora — як оновити backend на сервері з Windows

Ця інструкція пояснює, як передати зміни з вашого комп'ютера на Debian-сервер за допомогою готового скрипта `api/deployment/update/deploy.sh`.

## Коротка команда після змін

Збережіть змінені файли в редакторі, відкрийте **Git Bash** і виконайте:

```bash
cd /d/code/node_xora
bash apps/api/deployment/update/deploy.sh
```

Дочекайтеся повідомлення `Deployment complete`. Потім відкрийте [Swagger UI](http://192.168.1.33/api/).

Попередньо підключатися до сервера через `ssh` не потрібно: скрипт сам установлює SSH-з'єднання, копіює збірку й перезапускає API.

Ця інструкція описує поточну локальну версію. Зміни стають доступними на сервері лише після успішного запуску скрипта; самі правки файлів у Windows сервер не оновлюють.

## 1. Що де знаходиться

| Місце | Призначення |
|---|---|
| `D:\code\node_xora` | Локальний Git-репозиторій на Windows |
| `D:\code\node_xora\apps\api` | Вихідний код backend, який ви редагуєте |
| `apps/api/deployment/update/deploy.sh` | Скрипт оновлення; запускається на Windows у Git Bash |
| `dvor@192.168.1.33` | Користувач і адреса Debian-сервера |
| `/home/dvor/nodexora/api` | Готова запущена збірка на сервері |
| `http://192.168.1.33/api/` | Swagger UI через Nginx |

Робочий цикл: **змінити локальний код → зберегти файли → запустити скрипт → перевірити API**.

Скрипт оновлює лише backend. `apps/web` не збирається й не копіюється. Зміни лише в Angular не будуть опубліковані цією командою.

## 2. Як відкрити Git Bash

Git Bash встановлюється разом із **Git for Windows**. Для цієї інструкції відкривайте саме Git Bash; команда `bash` у PowerShell може запускати інше Linux-середовище, наприклад WSL.

Можна відкрити меню Windows, знайти **Git Bash** і запустити його. Потім перейти в проєкт:

```bash
cd /d/code/node_xora
```

Або відкрити `D:\code\node_xora` у Провіднику, натиснути правою кнопкою й вибрати **Open Git Bash here**. У Windows 11 цей пункт може бути в меню **Показати додаткові параметри**.

У Git Bash шлях Windows `D:\code\node_xora` записується як `/d/code/node_xora`.

Перевірити поточну папку:

```bash
pwd
```

Очікувана папка — `/d/code/node_xora`.

## 3. Що має бути готове перед запуском

- Сервер увімкнений і доступний за `192.168.1.33` із вашої мережі.
- На Windows доступні Node.js, npm, Git Bash, SSH, SCP і tar.
- Локальна й серверна версії Node.js належать до однієї основної гілки; зараз це **26.x**.
- SSH-ключ знаходиться в `C:\Users\alexm\.ssh\id_ed25519_hermes_server`.
- На Debian уже є наше розгортання й налаштований маршрут Nginx `/api/`.
- User service `nodexora-api.service` встановлений і enabled; user lingering увімкнено. Для поточного сервера це вже налаштовано.

Це скрипт **оновлення наявного API**, а не першого встановлення сервера. Потрібні налаштування для поточного сервера вже створювалися; після перевстановлення Debian їх потрібно буде відновити окремо.

Перевірити локальну наявність команд можна так:

```bash
node --version
npm --version
ssh -V
tar --version
```

## 4. Як передати свої зміни

1. Внесіть зміни в `apps/api` у редакторі.
2. Збережіть файли. Скрипт читає файли з диска, а не незбережений текст у редакторі.
3. У Git Bash виконайте:

```bash
cd /d/code/node_xora
bash apps/api/deployment/update/deploy.sh
```

Якщо Git Bash уже відкритий у папці `apps`, команда інша:

```bash
bash api/deployment/update/deploy.sh
```

Якщо ви вже в `apps/api`:

```bash
bash deployment/update/deploy.sh
```

Це три способи запустити **той самий** скрипт. Використовуйте лише один, відповідно до поточної папки.

Окремо виконувати `npm run build`, вручну створювати архів або копіювати файли через `scp` перед цим не потрібно — усе входить у скрипт.

Git commit і push не є умовою запуску: скрипт використовує поточні збережені файли. Сам він не створює commit і не відправляє зміни до GitHub. Зберігати історію змін у Git потрібно окремо.

## 5. Що робить скрипт

| Повідомлення в терміналі | Що відбувається |
|---|---|
| `1/4 Install, type-check, test and build locally.` | Встановлення локальних залежностей за lockfile, перевірка типів, тести та збірка TypeScript у JavaScript |
| `2/4 Create staging directory...` | Створення тимчасової папки на Debian для нової версії |
| `3/4 Copy compiled JavaScript...` | Копіювання лише `dist`, `package.json` і `package-lock.json` через SSH |
| `4/4 Verify Linux release...` | Встановлення production dependencies на Debian, перевірка Linux provider, перезапуск API й перевірка через Nginx |

Локальна збірка створюється у свіжій тимчасовій папці. Архів містить лише `dist`, `package.json` і `package-lock.json`. README, план, TypeScript source, тести та deployment-скрипти залишаються в локальному репозиторії.

Команди активації виконуються через SSH без збереження скрипта в папці API. Після встановлення Linux-залежностей у `/home/dvor/nodexora/api` знаходяться тільки `dist`, `package.json`, `package-lock.json` та production `node_modules`. Окремого `release.json` більше немає.

`node_modules` із Windows не копіюється: сервер сам установлює production dependencies для Linux. SSH-ключі й локальні `.env` також не включаються в архів.

Скрипт не змінює Nginx, не запускає `apply-nginx.sh` і не потребує `sudo`. Поточний API запускається без додаткових облікових даних.

Не закривайте термінал під час оновлення. Для заміни процесу є коротке переривання доступності API; це не оновлення без простою.

## 6. Як зрозуміти, що оновлення завершене

Наприкінці успішного запуску буде приблизно такий текст:

```text
Deployment complete: /home/dvor/nodexora/api (systemd user service nodexora-api.service). Nginx unchanged.
Swagger: http://192.168.1.33/api/
```

Тепер процесом керує user service `nodexora-api.service`, а не окремий запуск через `nohup`.

Відкрийте:

- [Swagger UI](http://192.168.1.33/api/) — список доступних endpoints і можливість їх перевірити.
- [Health-check](http://192.168.1.33/api/v1/health) — перевірка відповіді API.

Очікувана відповідь health-check:

```json
{"data":{"status":"ok"}}
```

Для перевірки RAM у Swagger відкрийте endpoint пам'яті й натисніть **Try it out → Execute**. Додаткові заголовки та вхід не потрібні. Захист API відкладено на окремий майбутній етап.

## 7. Що робити, якщо виникла помилка

| Ситуація | Дія |
|---|---|
| `No such file or directory` для скрипта | Виконайте `pwd` і перевірте шлях команди за розділом 4 |
| `node` або `npm` не знайдено | Перевірте встановлення Node.js у Windows і перевідкрийте Git Bash |
| Помилка TypeScript або тестів | Виправте локальний код і повторіть запуск; до копіювання на сервер скрипт не дійде |
| SSH key not found | Перевірте файл ключа або задайте `SSH_KEY`, як у розділі 8 |
| `Permission denied (publickey...)` | Перевірте SSH-доступ і правильність ключа; не надсилайте приватний ключ чи пароль у чат |
| Сервер недоступний / timeout | Перевірте, чи він увімкнений і чи доступна адреса `192.168.1.33` |
| Node.js major versions differ | Узгодьте основну гілку Node.js локально й на сервері |
| Another deployment is running | Дочекайтеся іншого запуску; не видаляйте lock-файл для обходу блокування |
| API не пройшло перевірку після заміни | Скрипт спробує відновити попередню версію; прочитайте повідомлення про результат rollback |

Якщо підключення запитує passphrase до SSH-ключа, вводьте її лише у власному терміналі. Перевіряйте fingerprint сервера перед першим підтвердженням нового host key.

Помилка встановлення залежностей або перевірки нової збірки **до зупинки старого процесу** залишає поточний API запущеним. Помилка після початку заміни запускає спробу відкату. Успіх rollback не гарантується — скрипт повідомляє, якщо відновлення також не вдалося.

Для діагностики можна прочитати останні рядки серверного логу з Git Bash:

```bash
ssh -i "$HOME/.ssh/id_ed25519_hermes_server" dvor@192.168.1.33 \
  'journalctl --user -u nodexora-api.service -n 50 --no-pager'
```

При помилці на сервері може залишитися staging-папка для діагностики; її шлях буде виведено. Не видаляйте навмання папки або процеси. Якщо потрібна допомога, збережіть текст помилки, прибравши можливі секрети.

## 8. Інший SSH-ключ або адреса

Для поточного сервера достатньо звичайної команди з розділу 4. За потреби параметри можна задати лише для одного запуску:

```bash
DEPLOY_HOST=dvor@192.168.1.33 \
SSH_KEY="$HOME/.ssh/id_ed25519_hermes_server" \
bash apps/api/deployment/update/deploy.sh
```

Цей приклад запускається з кореня `node_xora`. Змінні не змінюють файл скрипта. Інший сервер повинен мати такі самі необхідні передумови розгортання.

Довідка без запуску оновлення:

```bash
bash apps/api/deployment/update/deploy.sh --help
```

## 9. Важливі межі поточного запуску

- Backend працює звичайним користувачем, без root.
- Node.js слухає loopback-порт 3000; браузер звертається через Nginx на порту 80.
- Налаштовувати SSH-тунель або відкривати порт 3000 для мережі не потрібно.
- API запускається автоматично під час завантаження Debian через `systemd` user service; `Linger=yes` уже ввімкнено для `dvor`. Увімкнення Windows-комп'ютера не потрібне.
- Поточний локальний API доступний через HTTP без автентифікації. HTTPS та захист доступу можна додати окремим майбутнім завданням.

Подальші роботи: [план моніторингу](api/MONITORING_PLAN.md). Деталі backend: [API README](api/README.md). Архітектура: [PROJECT_SPEC.md](PROJECT_SPEC.md).

## 10. Автозапуск після ввімкнення Debian

На сервері встановлено `/home/dvor/.config/systemd/user/nodexora-api.service`.
`systemd` запускає готовий `dist/server.js` від користувача `dvor`; збирати проєкт
при кожному boot не потрібно. `Linger=yes` забезпечує запуск user manager без входу
через SSH, а enabled unit підключається до його `default.target`.

Після входу через SSH керуйте API такими командами:

```bash
systemctl --user status nodexora-api.service --no-pager
systemctl --user restart nodexora-api.service
journalctl --user -u nodexora-api.service -n 50 --no-pager
```

Звичайне оновлення з Windows виконується тією самою командою `bash apps/api/deployment/update/deploy.sh`.
Скрипт керує цим сервісом; додатковий запуск `node` або `nohup` не потрібний.
API та Nginx перевірені після service stop/start. Сервер для цієї перевірки не
перезавантажувався, тому фактичний boot-тест ще не виконувався.
